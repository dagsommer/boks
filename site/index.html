What you get

A sandbox is its own virtual machine with its own kernel — and everything else follows from taking that boundary seriously.

A VM, not a container

Each sandbox boots its own Linux kernel under a hypervisor. The guest reports its own kernel, its own uptime, its own memory — a shared-kernel container can produce none of that.

Security model

Your directory, nothing above it

The workspace appears in the guest at its exact host path. Writes reach your files; parent directories are not exposed; a symlink pointing at ~/.ssh resolves inside the guest, not on your host.

Workspaces

A network you decide about

Every TCP connection the guest opens is judged on the host, by address and port, before anything is dialled — a guest that ignores the proxy is judged, not unfiltered. --net none gives it nothing at all.

Network policy

Keys that never enter the sandbox

The guest holds a placeholder; the host attaches your real credential only on requests to the hosts you named. boks secret set anthropic is the whole configuration.

Credentials

Sandboxes that persist

Run the same agent in the same directory and you are back where you left off — packages, caches and shell state intact — until boks rm deletes it cleanly.

Lifecycle

No account, no cloud, no telemetry

Everything runs on your machine. Nothing is sent anywhere, there is nothing to sign in to, and this page makes no third-party request either.

FAQ

First run

An agent, in a directory, inside a microVM of its own. The agent comes first and decides what the sandbox contains; the workspaces follow and default to the current directory.

The ten agents

# check the host, then get a shell in a microVM
boks doctor
boks run

# Claude Code, in one directory, and nothing above it
boks run claude ~/src/foo

# a policy that outlives the command that wrote it
boks policy init --preset locked
boks policy allow github.com:443

# or nothing it can reach at all
boks run --net none shell .
