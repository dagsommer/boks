Where it runs

Three answers, and only one of them is yes. Check this before you spend an hour on the setup.

Works

macOS on Apple silicon

The platform the VM boundary and the network policy were measured on.

Not verified

Linux with /dev/kvm

Built and designed for. Nobody on this project has exercised it end to end, so you would be the first.

Does not run

Windows

No native build. Inside WSL2 it should run unchanged — designed for, never executed. The whole analysis.

First run

An agent, in a directory, inside a microVM of its own. The agent comes first and decides what the sandbox contains; the workspaces follow and default to the current directory.

Prerequisites and the first run

Lifecycle, policy, credentials, ports

# build it, then check the host
make build
./bin/boks doctor

# a shell in the current directory
./bin/boks run

# Claude Code, in one directory, and nothing above it
./bin/boks run claude ~/src/foo

# nothing it can reach at all
./bin/boks run --net none shell .

What a sandbox is

Boks is the orchestration layer, not a hypervisor. Everything below the CLI is existing open-source software.

Your machine

boks CLI containerd containerd-shim-nerdbox-v1 libkrun
hypervisor boundary

microVM — its own kernel

  • workspace, via virtiofs, at its exact host path
  • your command

Assume code in the sandbox is hostile. The hypervisor is the boundary; in-guest permissions are not — the agent has root in the guest by design. Security model · Architecture

How this project talks about itself

The interesting thing about Boks is not the feature list. It is that the claims were tested, and the tests that failed were published rather than quietly fixed.

Measured, or not claimed

Every claim on this site is answerable to one document, which records what was observed and what each observation does not establish.
